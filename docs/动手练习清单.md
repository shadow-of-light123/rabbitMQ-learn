# 动手练习清单

按顺序做完这 8 个练习，面试考点就都覆盖到了。
**每一步都去管理台 <http://localhost:15672> 亲眼确认**，这是学 MQ 最重要的事 —— 看见消息在动。

> 启动前确认：RabbitMQ 在跑（`tools\start-rabbitmq.bat`），应用已启动（`./mvnw spring-boot:run`）

## 练习 1：看清 Exchange → Queue → Consumer 的完整链路

```bash
curl -X POST http://localhost:8081/demo/send/1
```

**观察点：**
1. 应用日志出现 `📤 已发送订单消息` → `✅ [Confirm] 消息成功到达 Exchange` → `📥 收到订单消息` → `✅ 订单处理成功并已 ACK`
2. 管理台 **Queues** 页，`order.business.queue` 的 Ready 数会瞬间 +1 又归 0

**要理解：** Confirm 回调是**异步**的，日志顺序不一定严格按照上面排列。

## 练习 2：验证 Return 回调（路由失败的坑）

```bash
curl -X POST http://localhost:8081/demo/send-nowhere
```

**观察点：** 日志出现 `⚠️ [Return] 消息路由失败(未进任何队列)!`

**关键实验：把 mandatory 关掉，看会发生什么。**

编辑 `src/main/resources/application.yml`：
```yaml
spring.rabbitmq.template.mandatory: false   # 改成 false
```
重启后重新调用这个接口 —— **Return 回调不再触发，消息凭空消失**。

> 这就是面试常问的："消息发出去但没进队列，你知道吗？"
> 不开 mandatory 就是**静默丢弃**，生产环境的经典事故来源。

**记得改回 `true`。**

## 练习 3：死信队列的完整触发过程

```bash
curl -X POST http://localhost:8081/demo/send-fail
```

`orderId=100` 能被 10 整除，业务逻辑故意抛异常。

**观察日志的完整过程：**
```
📥 收到订单消息, deliveryTag=1, redelivered=false
❌ 订单处理失败
🔁 第 1 次失败，消息重新入队等待重试          ← basicNack(requeue=true)
📥 收到订单消息, deliveryTag=2, redelivered=true
❌ 订单处理失败
🔁 第 2 次失败，消息重新入队等待重试
📥 收到订单消息, deliveryTag=3, redelivered=true
❌ 订单处理失败
💀 重试次数已用完(2 次)，送入死信队列         ← basicNack(requeue=false)
💀 [死信队列] 收到处理失败的订单，需人工介入
```

**管理台确认：** `order.failed.queue` 里有一条消息，且它的 header 里有 `x-death` 字段。

### ⚠️⚠️ 本项目实际踩到的两个坑（面试讲出来很加分）

开发这个功能时踩了两个真实的坑，都是生产环境常见事故：

**坑 1：不能依赖 `isRedelivered()` 判断重试次数**

最初代码用 `message.getMessageProperties().isRedelivered()` 判断"是否重试过"。
实测发现：`redelivered` 只表示"这条消息之前投递过"，**它不能表示重试了几次**。
结果消息在「失败 → requeue → 再失败」之间循环，**永远进不了死信队列** ——
就是经典的**无限重试风暴**。

现象证据：`order.business.queue` 累计投递 68 次、发布 59 次（多出 9 次重试），
但 `order.failed.queue` 投递数始终为 **0**。

> **正确做法**：用显式计数。生产环境用 Redis `INCR` + `EXPIRE`，
> 或者直接读消息 header 里的 **`x-death`** 字段 —— 消息每次经过 DLX 时
> Broker 会自动累加其中的 `count`，这是原生免费的重试计数。
>
> 更好的方案是**延迟重试队列**：失败后把消息发到 TTL 递增的队列
> （retry.1s / retry.5s / retry.30s），到期回到主队列。
> 重试间隔可控、不占用消费者、次数由队列层级天然决定。

**坑 2：幂等标记的写入时机（更隐蔽、更危险）**

最初把「检查 + 标记」合成一个方法，在业务逻辑**之前**调用。结果是：

```
第 1 次投递：标记为已处理 → 业务失败 → 消息 requeue
第 2 次投递：发现已被标记 → 判定为"重复消息" → 直接 ACK 丢弃 ❌
                                    ↑ 重试被误当成重复，消息永久消失
```

**一次失败的尝试就把 messageId 永久"毒化"了** —— 后续重试全被丢弃，
既无法重试成功，也永远进不了死信队列。消息就此凭空消失，且毫无告警。

> **正确做法**：把「检查」和「标记」**拆成两步**，只在业务**成功之后**才写入标记：
> ```java
> if (idempotentService.isProcessed(id)) { ack; return; }  // ① 只读检查
> doBusiness();                                             // ② 可能失败
> idempotentService.markProcessed(id);                      // ③ 成功了才标记
> channel.basicAck(deliveryTag, false);
> ```
>
> 这个坑很值得记：**幂等和重试是相互作用的**。
> 幂等做错了，会把重试机制一起毁掉。

## 练习 4：延迟队列（订单超时取消）

```bash
curl -X POST http://localhost:8081/demo/send-delay/777
```

**时间线：**
- t=0s：消息进入 `order.delay.queue`，管理台看到 Ready=1
- t=0~30s：消息**停在延迟队列不动**（TTL 倒计时中）
- t=30s：TTL 到期 → 变成死信 → 转到 `order.cancel.queue`
- 日志出现 `⏰ [延迟队列] 订单超时未支付，执行自动取消: orderId=777`

**要理解（面试加分点）：** TTL 方案只检查**队首**消息。
发一条 TTL=30s 的，再发一条 TTL=1s 的，**后者要等前者过期后才会被处理**。
这就是为什么生产环境更推荐延迟插件或定时扫表。

## 练习 5：重复消费与幂等

```bash
curl -X POST http://localhost:8081/demo/send-duplicate
```

用**同一个 messageId** 发了 3 条消息。

**观察日志：**
```
📥 收到订单消息, messageId=dup-xxx      → 处理成功
🔁 检测到重复消息，已跳过: messageId=dup-xxx   → 直接 ACK
🔁 检测到重复消息，已跳过: messageId=dup-xxx   → 直接 ACK
```

```bash
curl http://localhost:8081/demo/stats    # 看"幂等已记录消息数"=1
```

**要理解：** 幂等不是"防止消息重复"，而是"重复了也不影响结果"。
`IdempotentService` 用的是内存 Set，**重启即失效** —— 生产必须换 Redis 或数据库唯一索引。

## 练习 6：四种 Exchange 的路由差异

```bash
curl -X POST http://localhost:8081/demo/exchanges
```

发了 6 条消息（Direct 2 条、Topic 2 条、Fanout 1 条、Headers 1 条）。

**去管理台 Queues 页对比各队列收到的数量：**

| 队列 | 收到 | 为什么 |
|---|---|---|
| `learn.direct.queue` | **1** | key=`order.create` 匹配；`order.other` 不匹配被丢弃 |
| `learn.topic.order.queue` | **1** | 绑定 `order.*`，匹配 `order.created` |
| `learn.topic.pay.queue` | **1** | 绑定 `pay.#`，匹配 `pay.wechat.success` |
| `learn.fanout.sms.queue` | **1** | fanout 广播，忽略 RoutingKey |
| `learn.fanout.email.queue` | **1** | 同上 |
| `learn.headers.queue` | **1** | header 满足 `type=order` 且 `region=cn` |

**动手改一下：** 把 `RabbitConfig` 里 topic 的绑定从 `order.*` 改成 `order.#`，
重启后再发一次 —— 观察差异（这里两种写法结果相同，因为 key 只有一个单词）。

再试试把发送的 key 改成 `order.created.vip`：
- `order.*` → **收不到**
- `order.#` → **能收到**

这就是 `*` 和 `#` 的核心区别。

## 练习 7：消息积压与限流

先制造积压：

```bash
curl -X POST http://localhost:8081/demo/flood/500
```

**观察管理台：** `order.business.queue` 的 Ready 快速上涨。
管理台首页的 **Message rates** 图能看到 publish rate 远高于 deliver rate。

**实验 A：调大 prefetch**

```yaml
spring.rabbitmq.listener.simple.prefetch: 50    # 从 1 改成 50
```

重启后重新 flood，观察消费速度变化。

**实验 B：调大并发**

```yaml
spring.rabbitmq.listener.simple.concurrency: 5
spring.rabbitmq.listener.simple.max-concurrency: 10
```

**要理解：**
- `prefetch` 是**按 channel** 生效的，不是按队列
- prefetch 太小 → 吞吐低（每条都要往返 Broker）
- prefetch 太大 → 内存压力大、负载不均
- **⚠️ 注意：一旦把 concurrency 调成 >1，消息就失去顺序性了**

## 练习 8：消息顺序性（亲手破坏它）

想亲眼看到乱序，需要让消费有耗时差异。

**步骤：**
1. 把 `application.yml` 的 `concurrency` 改成 `5`
2. 把 `OrderConsumer.doBusiness` 改成随机 sleep（0~500ms）
3. 连发 10 条 orderId 递增的消息
4. 观察日志里 `orderId` 的**出现顺序 ≠ 发送顺序**

```java
// doBusiness 里加
Thread.sleep(new Random().nextInt(500));
```

**要理解：** 这就是为什么 RabbitMQ 不保证全局顺序。
面试如果被问"怎么保证顺序"，标准答案是：
- 单队列单消费者（`concurrency=1`）—— 吞吐低
- 按业务 key hash 分队列，同 key 进同队列 —— **推荐**
- 或者业务上规避（状态机 + 版本号，旧消息丢弃）

**记得改回去。**

## 综合挑战：把「订单超时自动取消」做完整

当前版本是"发出延迟消息后无条件取消"。真实业务要加两个保护：

**挑战 1：支付后取消延迟消息**
用户支付成功后，那条延迟消息应该失效。
提示：查库确认订单状态，已经是"已支付"就跳过取消。

```java
@RabbitListener(queues = MqConstants.ORDER_CANCEL_QUEUE)
public void handleOrderCancel(OrderMessage order, ...) {
    // TODO: 加了状态检查，只有仍是"待支付"才取消
}
```

**挑战 2：幂等保护取消操作**
如果同一条延迟消息被投递两次，不能重复取消（比如重复退款）。

**挑战 3：给失败订单加告警**
死信队列收到消息时，模拟发送告警（打日志 / 调 webhook）。
