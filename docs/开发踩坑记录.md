# 开发踩坑记录

本文档记录搭建这套 Demo 时**实际踩到的坑**，都是生产环境的真实事故类型。
面试时讲这些比背八股有说服力得多。

## 坑 1：Spring Boot 4 用的是 Jackson 3，不是 Jackson 2

**报错**：
```
java.lang.NoClassDefFoundError: com/fasterxml/jackson/databind/json/JsonMapper
Caused by: java.lang.ClassNotFoundException: com.fasterxml.jackson.databind.json.JsonMapper
```

**原因**：Spring Boot 4 / Spring Framework 7 已迁移到 **Jackson 3**，
包名从 `com.fasterxml.jackson` 变成了 `tools.jackson`。

看依赖树就很清楚：
```
+- org.springframework.boot:spring-boot-starter-amqp:jar:4.1.1
|  +- org.springframework.boot:spring-boot-starter-jackson:jar:4.1.1
|  |  \- tools.jackson.core:jackson-databind:jar:3.1.5     ← Jackson 3
```
**Jackson 2（`com.fasterxml.jackson.databind`）根本不在 classpath 上。**

**解法**：用不带 `2` 的 `JacksonJsonMessageConverter`：

```java
// ❌ 会炸：Jackson 2 的转换器
import org.springframework.amqp.support.converter.Jackson2JsonMessageConverter;
return new Jackson2JsonMessageConverter();

// ✅ 正确：Jackson 3 的转换器
import org.springframework.amqp.support.converter.JacksonJsonMessageConverter;
return new JacksonJsonMessageConverter();
```

**怎么确认该用哪个**：直接从 jar 的字节码里读类引用的包名
```bash
unzip -p spring-amqp-4.1.1.jar org/springframework/amqp/support/converter/JacksonJsonMessageConverter.class \
  | grep -ao "tools/jackson[a-zA-Z0-9/]*" | sort -u
# → tools/jackson/databind/json/JsonMapper
```

> **面试点**：Spring AMQP 里带 `2` 的都是给 Jackson 2 用的老类，新版用不带的那个。

## 坑 2：`isRedelivered()` 不能用来判断重试次数

**现象**：消息消费失败后疯狂重试，**永远进不了死信队列**。

**证据**：管理台统计显示
```
order.business.queue   累计发布=59  累计投递=68   ← 多出 9 次重试
order.failed.queue     累计发布=0   累计投递=0    ← 死信队列一条都没收到
```

**原因**：代码用 `message.getMessageProperties().isRedelivered()` 判断"是否重试过"。
但这个字段只表示**"这条消息之前投递过"**，它**不能表示重试了几次**。
在 `requeue=true` 场景下语义边界模糊，导致消息在
「失败 → requeue → 再失败」之间无限循环 —— 就是**无限重试风暴**。

**解法**：用**显式计数**。

```java
// ❌ 不可靠
boolean alreadyRetried = message.getMessageProperties().isRedelivered();

// ✅ 显式计数（生产环境用 Redis INCR + EXPIRE）
int attempt = retryCounterService.getAndIncrement(messageId);
if (attempt <= MAX_RETRY) {
    channel.basicNack(deliveryTag, false, true);   // 重新入队
} else {
    channel.basicNack(deliveryTag, false, false);  // 送死信
}
```

**生产环境的三种正确做法**：

| 方案 | 做法 | 优缺点 |
|---|---|---|
| **Redis 计数** | `INCR retry:{messageId}` + `EXPIRE` | 多实例共享；需引入 Redis |
| **延迟重试队列**（推荐） | 失败后发到 `retry.1s`/`retry.5s`/`retry.30s`，到期回主队列 | 间隔可控、不占用消费者、次数由队列层级决定 |
| **`x-death` 头** | 消息经过 DLX 时 Broker 自动累加 `count` | 原生免费；但只在进过 DLX 后才有 |

## 坑 3：幂等标记的写入时机（最隐蔽，会静默丢消息）

**现象**：消费失败的消息在重试时被**当作重复消息直接 ACK 丢弃**，
消息凭空消失且没有任何告警。

**原因**：把「检查 + 标记」合成一个方法，在业务逻辑**之前**调用：

```java
// ❌ 错误：检查和标记合在一起，且在业务之前
if (!idempotentService.tryMarkProcessed(messageId)) {  // 这里就写入标记了！
    channel.basicAck(deliveryTag, false);
    return;
}
doBusiness(order);   // 如果这里抛异常...
```

执行轨迹：
```
第 1 次投递：标记为已处理 → 业务失败 → 消息 requeue
第 2 次投递：发现已被标记 → 判定"重复消息" → 直接 ACK 丢弃 ❌
                                    ↑ 重试被误当成重复，消息永久消失
```

**一次失败的尝试就把 messageId 永久"毒化"了。**

**解法**：拆成两步，**只在业务成功后才写入标记**：

```java
// ✅ 正确
if (idempotentService.isProcessed(messageId)) {   // ① 只读检查，不写入
    channel.basicAck(deliveryTag, false);
    return;
}
doBusiness(order);                                 // ② 可能失败
idempotentService.markProcessed(messageId);        // ③ 成功了才标记
channel.basicAck(deliveryTag, false);
```

> **核心认知**：**幂等和重试是相互作用的**。
> 幂等做错了，会把重试机制一起毁掉 —— 消息既不重试也不进死信，直接消失。
> 这是最危险的一类 bug，因为**没有任何报错**。

## 坑 4：Maven 构建被 IDE 文件锁搞挂（本机特定）

**报错**：
```
Could not transfer artifact org.apache.maven.plugins:maven-resources-plugin:jar:3.5.0
  ...jar.123456.tmp -> ...jar
```

**表象是网络问题，实际不是。** 排查过程：

1. jar 其实**已下载成功**，sha1 与远程一致
2. `mv file.jar test.jar` 报 `Device or resource busy` → **文件被锁**
3. 锁来自 Trae IDE 的 Java 语言服务器（`redhat.java` 扩展）在索引 `.m2`
4. 更深一层：`_remote.repositories` 里记录的仓库 ID（`central`）与当前仓库 ID
   （`aliyun-public-xxx`）不匹配，导致 Maven **每次构建都重新下载重写该文件**，
   而文件被锁着 → 必然失败

**解法**：
```bash
cd ~/.m2/repository
find . -name "_remote.repositories" -delete   # 删掉标记，Maven 就信任本地副本
find . -name "*.tmp" -delete                  # 清理残留
```

> 原理：没有 `_remote.repositories` 文件时，Maven Resolver 把本地副本
> 当作"已安装"直接信任，不再尝试重写，从而绕开文件锁。

## 坑 5：企业网络拦截 Maven 中央仓库

**报错**：`curl: (35) schannel: failed to receive handshake, SSL/TLS connection failed`

**原因**：`repo.maven.apache.org` 被企业网络拦截。

**解法**：`~/.m2/settings.xml` 配阿里云镜像：
```xml
<mirrors>
  <mirror>
    <id>aliyun-public</id>
    <url>https://maven.aliyun.com/repository/public</url>
    <mirrorOf>*</mirrorOf>
  </mirror>
</mirrors>
```
同时 `.mvn/wrapper/maven-wrapper.properties` 里的 `distributionUrl`
也要改成阿里云，否则 Maven Wrapper 连本体都下不下来。

## 坑 6：RabbitMQ 与 Erlang 的版本强耦合

**差点装错**：Erlang OTP **29.1.2** + RabbitMQ **4.3.6** → **起不来**。

查 [官方兼容矩阵](https://www.rabbitmq.com/docs/which-erlang) 才知道：

| RabbitMQ | 支持的 Erlang | 上限 |
|---|---|---|
| 4.3.0 ~ 4.3.5 | 27.x | 27 |
| **4.3.6** | **27 ~ 28.x** | **28** |
| 4.3.7+ | 27 ~ 29 | 29 |

Erlang 29 要从 RabbitMQ **4.3.7** 才支持，而 4.3.7 当时还不存在。

**最终组合**：RabbitMQ **4.3.6** + Erlang/OTP **28.2** ✅

> **教训**：装 RabbitMQ 前**必须**先查兼容矩阵，不要默认"都装最新版"。
> Erlang 版本不匹配时 RabbitMQ 会直接启动失败，且报错信息不一定直白。

## 坑 7：日志管道缓冲导致看不到输出

**现象**：用 `./mvnw spring-boot:run | tail -50` 后台启动，
输出文件**始终是 0 字节**，完全看不到日志。

**原因**：管道会缓冲。`tail` 要等输入结束才输出，而 `spring-boot:run` 是长驻进程，
永远不结束 → 缓冲区永远不刷出。

**解法**：后台启动**不要加管道**，直接重定向输出到文件：
```bash
./mvnw -B spring-boot:run        # 交给后台任务机制写文件
```

> 通用教训：**长驻进程的日志不要接 `tail`/`head` 这类需要等 EOF 的命令。**
